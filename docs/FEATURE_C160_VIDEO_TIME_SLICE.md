# C160 — Reviewed video time-slice photo

**1 new experimental source workflow; 0 separate product fixes; 0 product scaffolding. Registered after verified source checks.** Video Project → Create video time-slice photo combines spatial bands from4/8/16 requested source moments into a separate PNG. Choose columns with time left-to-right or rows with time top-to-bottom. Each band stays at its original position in the decoded image; frames are not averaged, aligned or stretched into repeated thumbnails. Review the complete encoded PNG and every requested source sample time before explicitly opening the image in a separate local guest photo workspace. Original video, timeline and account draft remain unchanged.

The source range comes from the current selected clip's visible trim selection, clamped to its actual source bounds. Integer source-millisecond sample centers are distinct and lie inside the half-open selection; at least one millisecond per sample is required. Decoding requests nearest original frames, which may repeat or lie near an edge; exact decoder frame timestamps are not certified. Video captions, grades, crop/layout and source motion are excluded. Decoded aspect is retained without upscaling, at most512pixels per edge; every band must have positive spatial size. Changing frame dimensions refuses rather than mixing geometry. Output is a flattened SDR PNG, without HDR/profile or arbitrary-alpha codec precision guarantees. Seams can be abrupt.

## Ownership and resources

The dedicated controls own one current dialog stage, one worker request and one prepared-image lease. Parent checks bind the project, selection/trim, current source maps/durations, mode/account namespace, foreground state and generation. Close/pause/destroy cancels and disposes matching output; stale/duplicate/retained callbacks cannot replace or open another stage's image. Cancellation and the checked60second deadline are tested between provider/decoder calls; physically blocked framework calls may return later. Worker account checks are throttled to100ms between cheap cancellation/deadline checks, with exact UI-owner revalidation before publication and opening.

One frame is decoded/normalized at a time, with a96MiB initial heap-headroom check. API27+ requests scaled frames; older Android uses the existing8.3megapixel legacy decode bound. Every decoded original-duration check must match captured metadata. The fresh bitmap is PNG-encoded through a latched2MiB output budget with SHA-256. The preview is decoded from bounded, digest-verified PNG bytes, so the review shows that output rather than an unencoded intermediate. Errors/cancellation delete this attempt's file. Only this workflow's expired cache PNGs older than one day are cleaned.

Opening verifies the complete PNG bytes again, takes its one-use lease before launching the image activity, and releases its preview bitmap. This protects the handed-off temporary file through the parent's pause cleanup. Failed opening deletes it; successful opening transfers only the PNG with GUEST_BASIC and protected-original provenance, without account draft or privileges. Save an image project/export there to keep the temporary result. No media/query upload, automatic clipboard read or original-media write occurs.
