# C078 — Saved local photo color palettes

**1 new experimental source workflow; 0 separate fixes/scaffolding.** Save colors extracted from an edited photo as a named local palette, then reopen and copy them for later photos. This is separate from C064's transient extraction/copy; naming, swatches, copy controls, deletion and Undo are parts of one reusable-palette workflow. No full app build or device acceptance.

Photo editor → Color & light → Extract preview palette → Save palette retains the measured RGB swatches under a user-supplied name. Color & light → Saved color palettes reopens the shelf, lists palette names and color counts, and offers individual HEX copy or all codes together. Copy a code and paste it into an existing photo object's custom color field. Saving or copying does not automatically recolor an image. Empty-shelf guidance explains how to create the first palette.

The shelf supports up to 20 uniquely named palettes, each containing 1–8 distinct opaque RGB colors. Names accept 1–40 Unicode code points without control characters or malformed surrogate pairs. Duplicate names are refused; there is no silent replacement. Names are data, never paths. The white/black controls use the existing EditorChrome; swatches retain their actual colors and HEX labels. Deleting requires a separate confirmation, followed by an Undo screen. Undo refuses to overwrite a shelf changed since deletion or restore into another shelf. Closing that screen discards the in-memory Undo option.

## Storage and ownership

- `PhotoColorPalettes` contains immutable defensive snapshots, bounded names/colors/catalogues and a versioned codec. A SHA-256 checksum detects corrupt bytes; this is not encryption or authentication.
- `PhotoColorPaletteStore` receives the existing `PhotoPresetNamespace`: a shared local guest shelf or an account/API-specific hash. Native callers place files under `noBackupFilesDir/photo-palettes`; only names/RGB are written, not images, URIs, pixel buffers, credentials or source provenance. Palettes are local, not backed up or embedded in image projects. App-data removal/uninstallation can remove them.
- Reads are bounded to 16 KiB. Missing data is empty; malformed, oversized or unreadable existing data is not silently reset. Scoped paths reject aliases/symbolic links. Mutations serialize within the app process, write a same-directory temporary file, sync its descriptor, check request ownership, then rename. Failed/cancelled writes clean the temporary output and preserve prior shelf bytes. Tests do not prove directory durability under power loss or cross-process transaction locking.
- Android disk work runs on the existing photo worker. The saved-palette controller checks the captured editor state, source, namespace, loaded scope and foreground generation. Saved-palette dialogs close on pause; stale results are not published. The owner callback is checked at admission and immediately before rename. Underlying controls ignore repeat actions during a pending operation; the dialog cannot be cancelled mid-write except through Activity closure/pause.
- Clipboard writes require a user action and use the existing sensitive-clipboard flag on API33+. Clipboard handling remains under the OS; the feature performs no network upload, query logging or palette telemetry. Existing extraction/copy still works, and project/edit/session schemas are unchanged.

This uses existing Android/Java APIs and Noble's existing scoped namespace; no new runtime package, license burden, native media-search/ranking change or billing change. It does not add perceptual clustering, full-resolution measurement, automatic recoloring, palette export/import or cloud sync.
